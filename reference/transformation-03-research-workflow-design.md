# 改造 #3 设计：Research Workflow（Corrective RAG 变体）

> 对应 MISSION 第 3 项：问题分析 → 检索 → **判断证据充分性** → 工具调用 → 补充检索 → 综合回答。

---

## 零、先回答一个绕不开的问题：现在不是已经全绿了吗？

这是本设计必须先交代的事。改造 #2/#8 做完之后，20 题评估集上 A 类四项全满：

```
A.retrieval_recall 1.0   A.evidence_recall 1.0
A.verdict_accuracy 1.0   A.citation_ok_rate 1.0
```

那 #3 还补什么？**补的不是"答得对不对"，是"什么时候停、凭什么停、能不能审计"。**
下面三条都是从现有数据里读出来的，不是假想的。

### 证据一：检索轮数没有上界

现在整张图只有两个节点，**"要不要再查一次"完全交给模型**：

```
model ──tools?──→ tools ──→ model ──tools?──→ tools ──→ … ──→ END
```

实测轮数分布很不稳（同一份语料、同一批问题）：

| 轮次 | 观察到的题 |
|---|---|
| 2 次 | A01 / A02 / A03 / A06 / A07 / A08 |
| 5 次 | A04 / A11 |
| **12 次** | B04（rerank@5 那一轮，耗时 9.0 秒） |

B04 的问题是「这些论文是否使用声呐、LiDAR 或三维点云」—— 正确答案是"没找到"。
模型为了确认这件事，**连续查了 12 次**。没有任何东西阻止它查第 13 次。

> 面试语言：ReAct 循环里"继续还是停止"是模型的自由裁量权，不是系统的约束。
> 这在 demo 里看不出问题，在计费和延迟上会。

### 证据二：「未找到」是模型说的，不是系统判的

`NOT_FOUND_IN_CORPUS` 目前**只是一个提示词规则**（`instructions` 第 4 条）——
图上没有任何节点负责得出这个结论。后果是它不稳定：

| 题 | 183422 | 184316 | 184813 | 185322 |
|---|---|---|---|---|
| B06（是否用强化学习选 patch） | ❌ GROUNDED | ✅ | ✅ | ✅ |

同一个问题、同一份语料，**同一句话在四次运行里翻过一次**。当"未找到"由模型自由心证
产生时，它就会随采样抖动 —— 而这正是这个项目最想守住的行为（不把"没找到"说成"不存在"）。

更关键的是：**现在无法区分两种"未找到"**：

- 改写了 3 次查询、换过同义词、每次都是低分 → 可以理直气壮说"库中没有"
- 第一次查询分数低就收手 → 只能说"我没找到"

这两者对用户的含义完全不同，但当前系统的输出一模一样。

### 证据三：查询改写是"隐性在起作用"的

做证据级召回时发现的（见 `design-decisions.md` 决策八）：

| 检索用什么查询 | 12 道 A 类题中锚点全中的数量 |
|---|---|
| 评估题**原文** | **8 / 12** |
| Agent **改写后**的查询 | **12 / 12** |

也就是说，A05 / A08 / A09 / A11 这几题，**原文检索拿不到答案必需的那几句**，
是 Agent 自己把「A²RNet 的 SAP 模块推断的三类语义属性是什么？」改写成
「A²RNet SAP module three semantic attributes」才捞回来的。

这件事的意义有两面：

1. **好消息**：现在的 Agent 确实会改写查询，这是真本事，不是提示词的幻觉。
2. **坏消息**：它**没有任何保证**。改写发生在模型的自由生成里，没有预算、没有触发条件、
   也不会在第一次检索失败时被强制发生。评测里它恰好都做了。

> **#3 要做的，是把这三件事从"模型的自由裁量"变成"图的显式结构"。**

## 一、三态输出：sufficient / absent / insufficient

设计里最核心的一点是**「未找到」必须分两种**：

| 状态 | 含义 | 系统可以说什么 | **不可以**说什么 |
|---|---|---|---|
| `sufficient` | 找到了支撑 | 「根据论文 …（第 X 页）」+ 引用 | — |
| `absent` | **查过了**，语料里确实没有 | 「当前论文库中未涉及」 | ❌「不存在」「没有这种方法」 |
| `insufficient` | 这次没查好 | 「正在补充检索…」（内部状态，不该直接给用户） | ❌ 任何结论 |

`insufficient` 和 `absent` 的区别就是上面「证据二」说的那件事：
**前者是"我还没找够"，后者是"我找够了但没有"。** 把后者当前者，用户就得不到答案；
把前者当后者，用户就得到一个假的"库里没有"。

`absent` 仍然**绝不能升级成"不存在"** —— 库里没有 ≠ 世上没有。这条从 baseline 的
「无根据的否定」缺陷一路继承下来，是项目的底线行为。

## 二、图结构

```
                    ┌────────────────────────────────────┐
                    ↓                                    │
   analyze ──→ retrieve ──→ assess ──(insufficient ∧ 还有预算)──→ refine
                  ↑                  │
                  └──────────────────┘
                                     ├──(sufficient)──────→ synthesize ─→ END
                                     └──(absent)──────────→ synthesize ─→ END
```

| 节点 | 职责 | 确定性 / 概率性 |
|---|---|---|
| `analyze` | 拆解问题：要查什么、关键词与同义词、需要 search 还是 list | **概率性**（LLM，1 次） |
| `retrieve` | 对每个待查子问题执行检索，**保留分数与来源** | **确定性** |
| `assess` | 逐子问题判三态：阈值阀门 + 预算 + 语义方向 | **混合**（见下方取舍） |
| `refine` | 改写失败子问题的查询：同义词、拆子问题、中英互换 | **概率性**（LLM，每轮 1 次） |
| `synthesize` | 综合回答，**按三态限制措辞**，附 citation | **概率性**（LLM，1 次） |

### 预算（硬约束，写在图上）

    MAX_RETRIEVE_ROUNDS = 3

`round >= MAX` 时，`insufficient` **强制降级为 `absent`**。

这条不能交给模型 —— 模型不知道"已经试过几次该由谁负责"。降级成 `absent` 而不是
继续重试，是因为此时系统可以说的话最少（「没找到」），**宁可说少，不能说错**。

### 关于 `assess` 的判据（已实测选定，走了两段弯路）

一开始设计了三个方案：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A：确定性 | 阈值 + 预算 | **零额外 LLM 调用** | 判不了"材料相关但答非所问" |
| B：LLM 评委 | 让模型读候选段落判三态 | 每轮 +1 次调用 | 又是一个会抖的 LLM 判断 |
| C：混合 | 默认 A，信号含糊时升级 B | 大多数题零额外开销 | 实现稍复杂 |

**第一段弯路：用「向量 top-1」当确定性判据 —— 完全失效。**

`refine` 把「这四篇论文是否采用 Mamba」改写成
`Mamba state space model SSM architecture for ship re-identification person re-identification`。
里面塞满了 re-ID 词汇，于是在 re-ID 语料上**必然高分**，哪怕语料里根本没有 Mamba。

> **查询改写的目标（召回）和判定的目标（忠实）是冲突的。**
> 改写是为了让查询匹配到东西，所以它一定朝"能匹配上"的方向优化；
> 而判定需要查询忠实代表问题。拿改写后的查询当相关性判据，等于自己骗自己。

结论：判定必须用**未经改写的子问题原文**，检索才用改写后的查询。这两件事必须分开。

**第二段弯路：只看 7 个手挑用例，以为交叉编码器能干净分开。**

换成「用交叉编码器给**原始问题** × 检索到的段落打分」之后，7 个用例的结果非常漂亮：

    应回答  A08 5.769 / A11 1.261 / A01 6.326
    应拒绝  B01 -8.137 / C01 -7.334 / C02 -6.155 / 杂问 -7.069
    空隙 7.416，阈值可取 -2.45

**但一上完整的 20 题评估集就重叠了** —— 这又踩了一遍"小样本乐观"的坑，
和决策一里阈值校准那次是同一个错误。

**最终实测（20 题评估集，A 类应回答 / B+C 类应拒绝）：**

| 判据 | 应回答最低 | 应拒绝最高 | 错几题 |
|---|---|---|---|
| 向量 top-1 | 0.353（A11） | 0.470（B03） | **6+** |
| 交叉编码器（对原问题打分） | **-0.314**（A06） | **0.794**（B05） | **2** |

交叉编码器明显更好，但**仍然不是干净的分界线**（02 题交叉）。这不是实现问题，
是任务本身的性质：「这段材料能不能回答这个问题」是语义判断，一个 (问题, 段落)
打分函数做不干净。

**所以最终取的是「保守使用」**：阈值 `EVIDENCE_RETRY_THRESHOLD = -3.0`，
**只用来触发「明显不相关就再查一轮」，最终结论仍由 `synthesize` 读材料得出。**

两边的代价不对称，所以宁可少重试、不可误重试：

- 误触发重试 → 多花一轮调用，而且下一轮大概率还是查不到
- 漏触发重试 → 不要紧，`synthesize` 本来就要读一遍材料做最终判断

在 20 题上的实际效果：

    12 道 A 类题最低是 A06 的 -0.314  → 全部不触发重试，不受影响
    明显不相关的会被触发          → B01 -8.137 / B04 -3.705 / B06 -3.191 / C01 -7.334 / C02 -6.155
    落在中间的交给 synthesize      → B02 -1.258 / B03 -0.340 / B05 0.794

## 三之二、实际跑出来的结果（对比 ReAct 版）

两个 agent 并存、共用同一套工具与检索管线，用同一份评估集对比：

| 指标 | `oa-assistant`（ReAct） | `research-workflow` | |
|---|---|---|---|
| A 类 verdict | 1.0 | **1.0** | 打平 |
| A 类证据召回 | **1.0** | 0.833 | ⚠️ 掉 2 题（A05 缺 `first-order difference`、A09 缺 `identity-view pair`）|
| A 类概念覆盖 | 0.958 | 0.938 | 略降 |
| A 类引用合格 | 1.0 | 1.0 | 打平 |
| B 类 verdict | 1.0 | 0.833 | ⚠️ B06 翻了 —— 但它在 ReAct 版里也翻过，是已知的抖项 |
| C 类 verdict | 1.0 | 1.0 | 打平 |
| 平均上下文 | 22124 | **9423** | ✅ **−57%** |
| 平均工具调用 | 3.25 | **2.85** | ✅ |
| 平均耗时 | 5.0s | 4.9s | 打平 |

**诚实的结论：更省了，但没有更准。**

预先定好的判定标准是「A 类 verdict 掉下来就算失败」—— 它没掉（1.0），所以不算失败；
但证据召回掉了 2 题，所以也算不上干净的胜利。**它换到的东西目前是"成本 + 可审计性"，
不是"准确率"**：

- 上下文降 57%，工具调用降 12%
- 检索轮数有了硬上界（原来实测最高 12 次）
- 「未找到」变成有预算背书的结论，答案里能直接说清查了几轮
- 三态与轮数进了 state，可以被断言，不再只能从对话里猜

**当前不切换默认 agent**（仍是 `oa-assistant`）。等证据召回那一项至少追平再切。

## 三之三、还欠着的两条

1. **判不出「部分覆盖」**。`assess` 判的是「有没有捞到相关内容」，判不出「捞到的是否完整
   回答了子问题」。实测 A08：交叉编码器给 5.769（判 sufficient），但三属性里只有两个
   被检索到，第三个排在候选第 18 位。
   修法：让 `analyze` 顺带产出「答案需要包含哪几个要点」，`assess` 再逐条比对检索文本 ——
   **这才是 LLM 评委真正该上场的地方**（方案 B 的价值点在这里，而不是在判"相不相关"）。

2. **A05 / A09 的证据召回掉了**，需要看是子问题拆分的问题还是改写把查询带偏了。

## 三、怎么验证它确实变好了

沿用已有的两层工具，**不新造指标**：

| 要证明的事 | 用什么测 | 期望 |
|---|---|---|
| 没答坏 | `run_eval.py` 20 题 | A 类 verdict / 证据召回**不下降**（现在 1.0，没有上升空间，只能守） |
| 检索轮数受控 | `process.avg_tool_calls` + 逐题最大值 | 上界从"12 次"变成 ≤3 轮；尾延迟下降 |
| 「未找到」变稳定 | B 类 6 题的 verdict 跨多次运行 | 从"翻过一次"变成多次一致 |
| 改写不再是隐性能力 | `rank_bench.py` 的锚点报告 | 首次查询锚点全中率从 8/12 提升 |
| 过程可审计 | 最终状态里带 evidence 三态与轮数 | 新增字段，可断言 |

**最后一次特别说明**：A 类现在全 1.0，所以这个改造**不可能在 A 类上刷出更高的分**。
它的收益全在"不坏 + 更省 + 更稳 + 可解释"上。如果评估显示 A 类掉下来，
那就是改造失败了 —— 没有"用 B 类换 A 类"这种账可以算。

## 四、行业名字（面试用）

"检索 → 评估证据 → 不够就改写查询重检索 → 够了再综合" 是 **Corrective RAG（CRAG）**；
让模型自己决定何时检索、并反思检索质量的那一支叫 **Self-RAG**。

> 面试说法：「我实现的是 Corrective RAG 的一个变体：评估节点输出**三态**而不是二态，
> 并且把"预算耗尽"作为从 `insufficient` 降级到 `absent` 的**确定条件** ——
> 也就是说，系统只有在真的试够了之后才允许说「库里没有」，而不是让模型自己觉得够了就说。」

比"我加了个提示词让它别乱答"强得多，因为前者是**图上的结构**，可以被测试断言。

## 五、与改造 #2 / #8 的关系（已解除循环依赖）

原版设计里这三者是循环依赖的。现在不是了：

```
改造 #2（RAG 重写）  ✅ 已完成
   ├── 带分数的检索结果      → hybrid.py 返回向量分数与来源
   ├── rerank               → rerank.py（交叉编码器）
   └── metadata / citation  → 论文标题 + 页码
              ↓
改造 #3（本设计）           ← 阈值已由评估集校准为 0.35
              ↓
改造 #8（Evaluation）      ✅ 已完成
   └── 20 题评估集 + 证据级锚点 + 确定性名次基准
```

阈值 `RELEVANCE_THRESHOLD = 0.35` 由评估集校准得来（空隙 0.2685 → 0.3752），
`assess` 可以直接复用，不需要重新调。
