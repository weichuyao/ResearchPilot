# 改造 #3 设计草稿：Research Workflow（证据充分性判断）

> 对应 MISSION.md 里的第 3 项改造：
> 增加 LangGraph research workflow：问题分析 → 检索 → **判断证据充分性** → 工具调用 → 补充检索 → 综合回答。
>
> 本文所有数字均为**本机实测**（`handbook` collection，875 条向量，bge-m3，k=5）。

---

## 一、为什么现在的图做不到

现在的图只有两个节点：

```
model → tools → model → END
```

整张图上**没有任何一处**负责回答："检索回来的东西，够不够回答问题？"

- 模型只能看到工具返回的**文本**，看不到任何"相关性"数字。
- 工具用的是 `similarity_search(query, k=10)`——**只返回文本，不返回分数**（实测：该向量库对象上有 `similarity_search_with_relevance_scores`，但代码没用它）。
- 结果是：无论检索到什么都返回 10 条，模型也无从判断"这些够不够"。

**结论：系统缺的不是提示词，是图上的一个节点。**

---

## 二、实测依据：真实分数分布

同一个向量库，四种查询的 top-5 相关度分数（`similarity_search_with_relevance_scores`，0~1，越高越相关）：

| 查询 | 手册里有答案？ | top-1 分数 | 前 5 条分数 |
|---|---|---|---|
| `vacation benefits` | ✅ 有 | **0.8344** | 0.834 / 0.628 / 0.620 / 0.560 / 0.554 |
| `annual leave policy` | ✅ 有（换个问法） | **0.5660** | 0.566 / 0.476 / 0.465 / 0.454 / 0.454 |
| `宠物保险 pet insurance` | ❌ 主题相关但没这条 | **0.3661** | 0.366 / 0.357 / 0.304 / 0.304 / 0.301 |
| `zzzzz nonexistent qqqq` | ❌ 完全无关 | **0.3478** | 0.348 / 0.280 / 0.274 / 0.272 / 0.270 |

### 这张表说明三件事

**1. 阈值确实能分开"有证据"和"没证据"** ✅

- 有答案的两类：top-1 = 0.834 / 0.566
- 没答案的两类：top-1 = 0.366 / 0.348

取 **0.5 左右**作阈值：

| 情况 | 是否放行 | 是否正确 |
|---|---|---|
| vacation benefits | 放行 | ✅ 有证据 |
| annual leave policy | 放行 | ✅ 有证据 |
| 宠物保险 | 拦截 | ✅ 确实没这条 |
| zzzzz | 拦截 | ✅ 确实无关 |

**四个 cases 全部判断正确。** 所以"相关度达到某个值作为区分"这个思路是成立的——这是第一层。

**2. 但阈值高低是个真实的两难** ⚠️

`annual leave policy` 的 top-1 只有 **0.566**，而 `vacation benefits` 有 **0.834**——**同一个主题，只是因为手册用词偏 "vacation"**。

- 阈值设 0.6 → 放行 `vacation benefits`，**却会误杀 `annual leave policy`**（用户问 annual leave 就答不出来了）
- 阈值设 0.3 → 放行了 `宠物保险`（0.366）和 `zzzzz`（0.348）的无关内容

**所以阈值不能拍脑袋定，必须用评估集校准。** 这是改造 #8（Evaluation）的直接用途：跑一批已知答案的问题，画出"该放行 / 该拦截"的分数分布，再取分界点。

**3. 分数高 ≠ 内容有用** ⚠️

`vacation benefits` 的 top-1（0.8344）内容是：

```
Vacation benefits.
```

**一个标题，18 个字符，零信息量，但分数最高。**

因为分数衡量的是**"离查询多近"**，不是**"有多少信息"**。短标题和查询字面高度重合，所以分数虚高。

→ 这是 **rerank 存在的理由**：用一个专门的模型对"问题 + 候选段落"重新打分，而不是只看向量距离。
→ 这也是 **chunk 质量（改造 #2）** 的直接后果：切得太碎，标题被当成独立段落。

## 三、节点设计

### 3.1 输入

| 输入 | 为什么必需 |
|---|---|
| **原始问题** | 判断"够不够"必须有参照物。脱离问题，分数毫无意义 |
| **带分数的候选段落** | 就是"评分机制"。**当前系统缺这个，必须先由改造 #2 补上** |
| **本轮已用过的查询** | 避免下一轮重复检索同一个词（模型很容易重复自己） |
| **已重试次数** | 防止无限循环。**必须由图来限制** |
| **本次检索的 k / 覆盖范围** | 知道这次只看了 top-k，可能有偏。"没找到"和"找过了但没找到"不是一回事 |

### 3.2 处理：两个维度，不是一个

这是本设计的核心。判断要分两步：

| 维度 | 问的问题 | 谁来判 |
|---|---|---|
| **① 相关度** | 有没有材料离问题足够近？ | **分数 + 阈值**（确定性，可测） |
| **② 语义方向** | 这些材料是在**肯定**、**否定**，还是**只是擦边**？ | **必须由 LLM 读内容判断**（概率性） |

**为什么必须两个维度**：分数只能回答"像不像"，回答不了"说了什么"。

- 手册写「公司**不**为员工提供宠物保险」→ 分数**高**（字面直接命中）
- 手册只写健康/牙科/人寿保险 → 分数**中低**

如果只看分数，这两种会被混为一谈。必须读内容才能分开。

### 3.3 输出：三态，不是布尔值

```
sufficient     证据支持 —— 检索到明确论述该事实的材料
absent         明确未涉及 —— 材料主题相关，但没有论述该事实
insufficient   证据不足 —— 分数不够，或材料与问题无关
```

**注意 `absent` 和 `insufficient` 的区别**，这是整个设计里最容易被忽略、也最重要的一点：

| 状态 | 含义 | 系统可以说什么 | 系统**不可以**说什么 |
|---|---|---|---|
| `sufficient` | 找到了支撑 | 「根据手册：…」+ 引用 | — |
| `absent` | 找过了，手册确实没写 | 「**手册中未找到相关规定**」 | ❌「不存在」 |
| `insufficient` | 这次没找好 | 「正在补充检索…」 | ❌ 任何结论 |

**`absent` 绝不能升级成"不存在"。** 手册没写 ≠ 事实上没有（可能写在手册之外）。这就是"无根据的否定"。

### 3.4 分支

```
analyze_question
      ↓
   retrieve ←──────────────────┐
      ↓                        │
 check_evidence                │
      ├─ sufficient ──→ synthesize ──→ END
      ├─ insufficient ─→ refine_query ─┘   （重试计数 +1）
      └─ absent ──────→ synthesize（措辞受限）──→ END
```

**重试上限（硬约束）**：`retry_count >= 2` 时，`insufficient` 强制降级为 `absent`。
否则用户会看到无限循环——**这个上限必须写在图上，不能交给模型**（模型不知道"已经试过几次"这件事该由谁负责）。

### 3.5 各节点职责

| 节点 | 职责 | 确定性/概率性 |
|---|---|---|
| `analyze_question` | 拆解问题：要查什么、关键实体、可能的同义词 | 概率性（LLM） |
| `retrieve` | 调用 `search_papers`，**返回带分数的结果** | 确定性 |
| `check_evidence` | 阈值过滤 + 读内容判断语义方向 → 三态输出 | 混合（阈值确定 + LLM 判断） |
| `refine_query` | 改写查询：换同义词、拆子问题、换语言 | 概率性（LLM） |
| `synthesize` | 综合回答，**按 `absent` 限制措辞**，附 citation | 概率性（LLM） |

## 四、这套模式的行业名字（面试用）

"检索 → 评估证据 → 不够就改写查询重检索 → 够了再综合" —— 业界称之为：

- **Corrective RAG（CRAG）**：检索后加一个评估环节，不足则纠正
- **Self-RAG**：模型自己决定何时检索、并反思检索质量

面试里说"我实现的是 Corrective RAG 的一个变体，评估节点输出三态而不是二态"，比说"我自己想了个办法控制它别乱答"强得多。

## 五、依赖关系

```
改造 #2（重写 RAG）
   ├── 提供「带分数」的检索结果   ← 本设计的前提
   ├── 提供 rerank                ← 解决"分数高但没信息量"
   └── 保留 metadata              ← 提供 citation
              ↓
改造 #3（本设计：证据充分性节点）
              ↓
改造 #8（Evaluation）
   └── 校准阈值 ← 用已知答案的问题集，画出"该放行/该拦截"的分数分布
```

**注意这三者是循环依赖的**：#3 的阈值需要 #8 来校准，而 #8 的指标需要 #3 的三态输出来定义。**正确的做法是先用一个粗糙阈值跑通 #3，再用 #8 的评估集把阈值调准。**
