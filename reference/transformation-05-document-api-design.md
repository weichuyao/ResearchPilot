# 改造 #5 设计：文档上传与知识库 API

> 对应 MISSION 第 5 项：知识库、文档、会话、Agent Task、Health 等 API。
> 本文先做**文档上传**这一条链 —— 它是"知识库"这三个字的前提。
>
> **状态**：上传 / 列表 / 查询 / 删除 / 重索引 / 多格式 / `/health` 已实现；
> 前端入口是 Header 上的「知识库」抽屉。多格式与重索引的设计在文末第八、九节。

## 零、为什么现在做这个

### 现状：语料是冻结的

改造 #2/#3/#8 做完之后，检索层、两种 agent、评估体系都已经立住了。但它们**只能回答
`backend/resource/papers/` 里那 4 篇 PDF 的问题** —— 加一篇论文要手工跑
`python app/ai/rag/ingest.py`，而且那个脚本是**整库重建**（`reset=True` 先清空）。

这意味着：

| 现在做不到的事 | 后果 |
|---|---|
| 用户上传自己的论文 | 只能是个 demo，不是工具 |
| 增量加一篇 | 必须整库重建，4 篇变 5 篇要重嵌入全部 |
| 知道某篇导入成功没有 | 只能看脚本的标准输出 |

### 它还卡住了评估基础设施的复用

`reference/design-decisions.md` 里那一整套方法论（20 题评估集、证据级锚点、
确定性名次基准）是**为这 4 篇手写的**。只有当你能导入新语料时，这套方法才有复用价值 ——
否则它是一次性的考古工作。

## 一、接口设计

```
POST   /documents            上传一个 PDF → 202 + 文档记录（含 id 与 status）
GET    /documents            列出知识库里的文档
GET    /documents/{id}       查单个文档的状态（前端轮询这个）
DELETE /documents/{id}       删除文档（向量块 + 上传的文件 + 记录）
GET    /health               服务健康：代码版本、已加载的模型、索引统计
```

### 1.0 删除接口的三条约束

**① 删的顺序不能反：先删向量块，再删 paper 行。**
反过来的话，万一删向量失败，`source_file` 这个唯一能把两边对起来的键就没了 ——
那些向量块变成永远找不到、也永远清不掉的孤儿。先删向量则失败时记录还在，可以重试。
（删向量失败返回 **503** 而不是 500：它是下游依赖不可用，语义上属于「稍后重试」。）

**② 只删「自己管的」文件。**
`resource/papers/` 里那 4 篇是操作者放进去的种子语料，由 `ingest.py` 管理；
`resource/uploads/` 才是本接口的产物。所以磁盘删除**只允许发生在上传目录之内**，
判断用 `os.path.commonpath` 而不是字符串 `startswith` ——
`startswith("/a/uploads")` 会被 `/a/uploads-evil/x.pdf` 骗过去。
删库接口顺手把语料删了是不可逆的事故。

**③ 默认拒绝删除「处理中」的文档（409），另留 `?force=true` 出口。**
后台索引任务手里攥着 `paper_id`，跑完会去写状态。此时删记录：
状态更新会落空（`update_progress` 找不到行，静默返回 None），
但**向量块已经写进去了** —— 又一批孤儿。

那卡住的文档怎么办？`force=true` 就是给它们留的：进程重启会让后台任务消失，
记录永远停在「处理中」（`/health` 的 `index.by_status.indexing` 报的就是这个）。
**那种情况下没有任何任务会再写，强制删才安全** —— 换言之 force 只在
「你确认进程重启过」时才用。

> 返回 **204** 而不是 200 + body：项目里 `DELETE /employee/delete/{id}` 已经是 204。
> 「删掉了几个向量块」这类细节进日志，聚合效果看 `/health`。

### 1.0.1 一个 FastAPI 的坑：204 路由不能写返回注解

```python
async def delete_document(...) -> None:      # ← 会让 FastAPI 直接断言失败
```

因为 FastAPI 会从返回注解推断 `response_model`，而 **`NoneType` 这个类对象是 truthy 的**，
于是它认为"有响应体"：

```
AssertionError: Status code 204 must not have a response body
```

正确写法是**不写返回注解**（项目里 `delete_employee` 就是这么写的）。
这个坑值得记一下：错误信息指向的是「状态码不能有响应体」，看起来像是状态码写错了，
实际上问题在返回注解上。

### 1.1 为什么是 202 而不是 200

一篇 PDF 要**解析 → 清洗 → 切块 → 逐块算 embedding 写向量库**。实测 4 篇论文
411 个块，导入耗时以分钟计。**不可能让一个 HTTP 请求干等这么久** —— 网关、
浏览器、客户端超时都会先动手。

所以：**受理（202）= 已经收下并开始处理，不等于已经完成。** 返回文档记录，
前端拿着 id 去轮询 `GET /documents/{id}`。

`reference/http-status-codes.md` 里已经把这一条设计过了，这里只是落实。

### 1.2 为什么用 paper 记录当"任务"，而不新建一张 task 表

直觉做法是建 `IngestTask(id, paper_id, status, error, ...)`。**这里不这么做**，
理由是：

> 对「一篇论文」而言，同一时刻最多只应该有一个索引入库操作在进行。

既然操作天然按文档唯一，那 `paper.status` 本身就是任务状态，多一张表只会多一处
不一致的可能（task 说完成、paper 说失败）。而且这直接让 **409 的语义变得自然**：

```
同一篇论文正在处理中 → 再传一次 → 409 Conflict（不是错误，是当前状态不允许）
```

代价与边界要说清楚：**重复索引同一篇论文（比如换了切块参数想重跑）时，
这张模型表达不了"第几次任务"。** 现在用不上，真需要时再加 task 表，
那时它的字段会是 `attempt`、`started_at`、`error` 这些 —— 而不是现在提前臆想。

### 1.3 状态机

```
        POST /documents
              ↓
   [落盘 + 建 Paper 行 status=0 待处理]  ← 这一步在 HTTP 请求里完成，很快
              ↓  返回 202
   [后台线程：解析 → 切块 → 嵌入]
              ↓
      status=3 处理中 ──成功──→ status=1 已索引
              └────失败────────→ status=2 失败
```

`status` 取值沿用已有的 `db/models/paper.py`（0 待处理 / 1 已索引 / 2 失败），
**新增 3 = 处理中**。为什么必须把"排队"和"处理中"分开：后台任务跑在进程内，
进程重启会让任务丢失 —— 那时行会永远停在 3。有了独立取值，
`GET /health` 或启动时就能识别「重启前卡住的导入」，而不是把 0 和 3 混在一起。

## 二、最关键的一条：同步任务必须挪出事件循环

这是本次实现里最容易写错、后果最严重的一点。

`ingest` 这条链**全是同步阻塞的**：

- PDF 解析（pdfminer）和切块 —— **CPU 密集**
- `document_vector_store.add_documents()` —— **同步 HTTP 调 Ollama 算 embedding**

如果在 `BackgroundTasks` 里直接调用它，它会**跑在 FastAPI 的事件循环上**。
后果不是"这个上传慢"，而是**整个后端在这几十秒里停止响应** ——
包括其他人正在用的 SSE 聊天流。

所以后台执行要显式扔到线程里：

```python
await asyncio.to_thread(_blocking_ingest, ...)
```

> 一句话规则：**事件循环上不许有阻塞调用。** CPU 密集或同步 IO 的活儿，
> 要么 `await asyncio.to_thread(...)`，要么扔给独立 worker 进程。

（真正的生产做法是独立 worker + 队列（Celery / arq / RQ），那样服务重启不丢任务、
还能多副本。这里先用 `asyncio.to_thread`，因为它是**同一台机器上最小且正确的改动**；
分队列属于改造 #6/#9 的范畴。）

## 三、上传必须走增量，不能复用整库重建

`ingest()` 现在的语义是**整库重建**：`reset=True` 时先把 Chroma collection 清空。
上传接口绝不能这么干 —— 传第 5 篇会把前 4 篇抹掉。

所以要新增一条增量路径：

```
ingest_uploaded(path, source_file, ...) →
    只解析这一个文件 → 只追加它的块 → 只 upsert 它那一行 paper
```

### 3.1 顺带必须做的一件事：让 BM25 索引失效

改造 #4 里给检索加了 BM25 关键词召回，索引是**按 Chroma 集合大小做签名缓存的**
（`ai/rag/hybrid.py` 的 `get_index()`）。签名相同就复用缓存的索引。

后果：**新导入的文档如果不显式让缓存失效，BM25 那一路在进程重启前根本看不见它。**
向量那一路是直接查 Chroma 的，所以会命中 —— 于是现象是"语义能搜到、关键词搜不到"，
非常难查。`hybrid.py` 里已经预留了 `invalidate_index()`，增量导入结束时必须调用它。

### 3.2 还有两个必须处理的点

- **文件重名**：两篇不同论文都叫 `paper.pdf`。落盘时用内容哈希做文件名前缀，
  不用用户给的名字（用户给的名字不可信，也不该出现在磁盘路径里）。
- **清理**：解析失败时，已落盘的临时文件要删掉，`paper` 行标成 `status=2` 并记录原因 ——
  失败要**留在记录里**，不是只打一条日志。

## 四、校验的顺序与语义（`http-status-codes.md` 的落实）

顺序很重要：**先做便宜的检查，再做贵的**。

| 顺序 | 检查 | 不合格 | 为什么 |
|---|---|---|---|
| 1 | Content-Type / 扩展名 | **415** | 不花任何代价，最早拒 |
| 2 | 边读边算大小，超过上限立刻中断 | **413** | **不能先整个读进内存再判** —— 那样攻击者用 10 GB 文件就能打爆内存 |
| 3 | 同名/同内容论文是否已在处理中 | **409** | 业务规则 |
| 4 | 落盘、建记录 | — | 到这里才开始真正花钱 |
| 5 | 返回 **202** | — | |

第 2 条值得单独说：FastAPI 的 `UploadFile` 是 `SpooledTemporaryFile`，
**不读它就不会占内存**。所以要 `while chunk := await file.read(1MB)` 累加到
上限就断开，而不是 `await file.read()` 一把梭。

## 五、为什么顺手加 `/health`

因为今天已经因此吃过一次亏。

排查过程中发现：**后端进程跑的是几小时前的旧代码，而没有任何地方能看出来。**
`uvicorn` 没开 `--reload`，日志在隐藏窗口里，最后是靠手工比对进程启动时间才确认的。
在此之前我一直在用"新写的代码"解释旧进程的行为。

`/health` 应该回答三个问题：

```
{ "app": "ResearchPilot",
  "code":   { "started_at": ..., "git_rev": ..., },     ← 线上跑的是哪份代码
  "models": { "reranker": "loaded" | "unavailable" },   ← 重排模型加载了没
  "index":  { "papers": 4, "chunks": 411,
              "by_status": {"indexed": 4, "failed": 0, "indexing": 0} } }
```

`git_rev` 直接从 `.git` 读，不引入依赖。有了它，"我改的代码生效了吗"就是一次
`curl` 的事，不用再靠猜。

## 六、这一步**不做**什么（避免范围失控）

- **不做鉴权**。MISSION 的 Out of scope 里明确写了复杂鉴权不做。
- **不做多格式**（DOCX / Markdown）。`pdfminer` 只解决 PDF；多格式是解析器插件化
  的问题，等 PDF 这条链稳了再说。
- **不做向量库/关系库的分布式一致性**。先单进程单库。
- **不接 MCP**（改造 #4）。工具都在进程内，没有外部工具要接 —— 理由见下。

> 关于 #4 的取舍（写在设计文档里，面试会被问到）：
> MCP 的价值是**让进程外的工具能被标准化地发现与调用**。我们的 `list_papers` /
> `search_documents` 都是进程内函数，引入 MCP 只会多一层协议开销而没有任何收益。
> **等真的要接 arXiv / PubMed 检索时再做** —— 那时理由现成：工具来自进程外。
> 为 MCP 而 MCP，被追问「不用它会怎样」时答不上来。

## 六之二、实现时才暴露出来的两个坑

设计阶段没想到、写代码时才撞上的两个问题。都比它们看起来更值得记。

### 坑一：异步后台任务里「扔线程」和「碰数据库」不能同时做

第二节说了「同步任务必须挪出事件循环」。第一版实现照做了，但方式错了：

```python
def _ingest_in_background(...):        # 同步函数
    async def run():
        await mark(INDEXING)           # ← 用全局 async_session_maker 写数据库
        await asyncio.to_thread(index_pdf, ...)
    asyncio.run(run())                 # ← 在 Starlette 的线程里另起一个事件循环
```

看起来没问题：同步函数被 Starlette 丢进线程池，重活也扔了线程。
**但 `mark()` 用的是模块级的 `async_session_maker`，它的连接池是在主事件循环上建立的。**
在线程里另起一个 loop 去复用它，会抛
`Future attached to a different loop` —— 而且是**随机地**在某次请求上炸，不是每次都炸。

正确的拆法是**两部分都留在自己的地盘**：

```python
async def _ingest_in_background(...):      # async，跑在主循环上
    await mark(INDEXING)                   # 数据库 → 主循环
    row = await asyncio.to_thread(index_pdf, ...)   # 重活 → 线程池
    await mark(INDEXED)                    # 数据库 → 主循环
```

于是 `ai/rag/ingest.py` 里的逻辑也被迫拆成两个函数，各自只干一件事：

| 函数 | 在哪跑 | 碰什么 |
|---|---|---|
| `index_pdf` | 线程池 | 解析、切块、写向量库。**不碰关系库** |
| `record_paper` | 主循环 | 写 paper 表。**不做重活** |

> 一句话规则：**线程里只做纯计算和外部 IO，不碰那些在主循环上建立的异步资源。**
> 讽刺的是，这条和第二节那条是同一个道理的两面 —— 一个是「别阻塞循环」，
> 一个是「别偷另一个循环」。

### 坑二：加一个字段会把旧数据库搞崩

`Paper` 要加 `error` 列来记录导入失败的原因。但 **`metadata.create_all` 只会建
不存在的表，不会给已存在的表加列** —— 旧 `database.db` 拿不到这一列，
第一次查询就 `no such column`。

原来的做法一直是「删掉 database.db 重跑 ingest」，但那要求使用者知道这件事，
而且会丢掉所有人的论文记录。

所以在 `create_db_and_tables()` 里加了一个 `_add_missing_columns()`：
遍历 SQLModel 的 metadata，对已存在的表补上缺的列。
SQLite 从 3.2 起就支持 `ALTER TABLE ... ADD COLUMN`，而我们要补的恰好都是
**可空、带默认值的新列** —— 这是 SQLite 唯一能原地完成的 schema 变更。

⚠️ 明确标注为**临时手段**：只覆盖「加可空列」这一种情况。改造 #6 换 PostgreSQL 时
应该同时引入真正的 migration 工具（Alembic），那时删列、改类型、建索引才有的谈。

实测有效（`/health` 那次运行的日志）：

```
schema: 给 paper 补上新列 error
```

## 七、验收标准

一条端到端链走通，而不是接口返回 200 就算完：

1. 上传一篇**新的** PDF（不是已有 4 篇）→ 拿到 202
2. 轮询 `GET /documents/{id}` → 状态从"处理中"变成"已索引"
3. **用聊天问它里面的内容 → 能答出来并带页码引用**
4. `list_papers` 能列出 5 篇（结构化那一路也同步了）
5. 用关键词（BM25 那一路）也能搜到新文档 —— 验证索引缓存确实失效了
6. 传一个 `.txt` → 415；传超限文件 → 413；处理中重复传 → 409

第 3 条是真正的验收点：**前面全是手段，这一条才是目的。**

（注：上面第 6 条写"传一个 .txt → 415"是第一版的设计 —— 那时只支持 PDF。
现在 .txt/.md/.docx 都支持了，415 留给真正不认识的扩展名。）

测试脚本：`backend/tests/api/uploadApiTest.py`。它现场生成四种格式的测试文件，
跑完把向量块、记录、磁盘文件全部清掉，并断言清理后回到基线 ——
**测试不该改变被测试系统的状态。**

## 八、多格式：位置标签，而不是硬套页码

### 8.1 问题：Markdown 没有页

第一版把位置字段叫 `page`、把引用写死成 `p.5`。支持 Markdown 之后就出问题了：

> 引用写「第 2 页」，而那个文件**根本没有页**。

引用是用户唯一会核对的东西 —— **说错比不说更糟**。所以引入 `Section(label, text, kind)`：

| 格式 | kind | 前缀 | 标签含义 | 引用长这样 |
|---|---|---|---|---|
| PDF | page | `p` | 物理页码（1 起） | `p.5` |
| Markdown | section | `sec` | 第 N 个标题段落 | `sec.2` |
| DOCX | section | `sec` | 第 N 个标题段落 | `sec.3` |
| 纯文本 | block | `blk` | 第 N 个段落块 | `blk.4` |

前缀随块写进 metadata（`locator_prefix`），由 `format_hits()` 拼出引用。
「支持哪些格式」只在 `ai/rag/parsers.py` 的注册表里定义一处 ——
上传接口的校验、批量导入的目录扫描、错误信息里的格式清单，全从那里取。
写两份的话必然漂移，而漂移的表现是「传上去了但索引一直失败」。

### 8.2 改这个格式是有代价的，而且今天刚付过一次

工具输出的头部格式**是评估脚本的解析对象**。今天已经因为「改了输出格式、
解析正则没跟着改」导致 `retrieval_recall` 静默掉到 0.25 一次。

所以这次是**三处同步改**：

```
ai/rag/pipeline.py    format_hits()        拼出 `<prefix>.<label>`
ai/eval/run_eval.py   _SOURCE_RE           从写死 `p\.` 改成 `(?P<prefix>[a-z]+)\.`
ai/eval/run_eval.py   retrieval_hit 判定    加一个 source["prefix"] == "p" 的条件
```

最后那条不是可有可无的：评估集的 `expected_source` 给的是 **PDF 页码**，
而 Markdown 的 `sec.3` 里那个 `3` 是**章节号**。不区分就会假命中
（"第 3 节"被当成"第 3 页"）。

改完重跑评估：`retrieval_recall = 1.0`、`parse_warnings = 0` —— 没打坏。
那个自检就是为这类改动加的，它在这里确实起了作用。

### 8.3 解析和清洗分开

`parse()` 只把文件变成文本片段，**不清洗**。清洗是**格式相关**的，放在 `clean()`：

- PDF：跨页重复行（页眉页脚）+ 断词合并（`represen-` 换行 `tation`）+ 连字还原
- 其它：只做连字还原

把 PDF 那套规则套到 Markdown 上会把正常的硬换行也吃掉。
默认 `clean()` 只做字符还原，`PdfParser` 覆写它加更多步骤。

### 8.4 为什么表格不能跳过（DOCX）

技术文档里的参数表、对比表常常是**唯一**写清某个事实的地方 ——
「支持哪些格式」这类问题的答案往往就在一张表里。丢掉表格等于丢掉内容。
所以 DOCX 解析器把表格拼成 `单元格 | 单元格` 的行一起抽出来。

### 8.5 新依赖

`python-docx>=1.1.0`（带 `lxml`）。理由和加 `pdfminer.six` 一样：
**标准不是「能不能不加依赖」，而是「自己写的会不会更差」** ——
DOCX 是 zip + XML，自己解析要处理关系表、样式继承、合并单元格，不值当。

⚠️ DOCX 的魔数 `PK\x03\x04` 同时也是 zip 的魔数，所以校验是
「魔数 + 扩展名」两重，不能只看魔数。反过来，没有魔数的格式（Markdown / 纯文本）
做一次粗筛：前 4KB 里出现 NUL 字节就拒掉 —— 挡住「把 .exe 改名成 .md」，
否则它会被当乱码文本索引进库、污染检索。

## 九、重索引：不需要额外的 task 表

```
POST /documents/{id}/reindex   → 202（先清旧块，再走一遍索引）
```

存在的理由：上传接口对同一份文件返回 409，消息是「需要重新索引请先删除该文档」——
**在没有这个接口之前，那句话让用户去做一件他做不到的事。**

### 9.1 为什么必须先删旧块

**不删的话新块和旧块会叠加**：同一段内容在向量库里存在两份，检索时互相竞争，
引用看起来还很正常（同一页、两个不同分数）。这种重复**不会报错**，只会让结果变差。

删在前面的代价是：重新解析失败的话旧索引已经没了，文档变成 `status=failed`。
这个取舍是**故意**的：

| 做法 | 失败时的坏状态 | 看得见吗 |
|---|---|---|
| 先删后加（采用） | 文档变 failed，旧索引没了 | ✅ 记录里有 error |
| 先加后删 | 留下重复块，检索悄悄变差 | ❌ 完全看不出来 |

**宁可要一个看得见的失败，不要一个看不见的重复。**

### 9.2 为什么不需要 task 表（推翻自己的预测）

设计第一版说「真需要时再加 task 表」（见 1.2 节）。真做下来发现**不需要**：
「一篇文档同时只有一个索引操作」这个不变量对**重索引同样成立**，
所以 `paper.status` 依然够用。

task 表真正会被需要是在这些场景 —— 现在一个都不成立：

- 需要**操作历史**（第几次、什么时候、失败原因）
- 需要**批量重索引整个知识库**（任务就不挂在单个文档上了）
- 要**多 worker 并发**（那时需要跨进程的任务认领机制）

**提前建表只会多一处不一致的可能。** 这条比「按计划建表」更值得记：
设计文档里的预测也要拿实现去校验，不能因为是"自己写的计划"就照做。

## 十、前端的边界

Header 上加了「知识库」按钮，抽屉里可以上传、看进度、重索引、删除。

三条前端原则：

1. **上传成功 ≠ 能检索到。** 后端返回 202（受理），所以只要列表里还有
   pending/indexing 的文档就每 1.5 秒轮询一次，两种状态分开展示。
2. **后端的 `detail` 原样显示。** 那些话是特意写成给人看的
   （「文件超过 50 MB 上限」「这篇论文已经在知识库里了（id=5）」）。
   前端统一换成「上传失败，请重试」就把信息全丢了 ——
   用户就不知道是文件太大、格式不对、还是重复了。
3. **不在前端抄一份大小上限。** 规则在后端，抄一份就会漂移，
   用户会遇到「界面说可以传、后端说太大」。前端只做 `accept` 过滤。

⚠️ `accept` 里的扩展名是后端解析器注册表的**手工镜像**，两边必须同步。
改造 #10 应该把它改成从后端动态取（加一个 `GET /documents/formats`）。
AgentSelector 里的 agent 列表也是同一类问题。

## 十一、还没做的

| 项 | 为什么现在不做 |
|---|---|
| **批量重索引整个知识库** | 需要把任务从"挂在文档上"改成独立的队列，是 9.2 说的三种场景之一 |
| **切块参数记录在文档上** | 换 chunk_size 之后无法从接口看出哪些文档是旧参数索引的。加两列即可（mini-migration 已经能加列），但先看有没有真实需求 |
| **鉴权** | MISSION 的 Out of scope 明确写了不做 |
| **文档内容预览** | 需要在向量库上做"按 source 取原文"，现在只能靠检索命中 |
