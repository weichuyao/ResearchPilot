# HTTP 状态码速查（够用版）

> 从第 4 课延伸出来的参考件。目标不是背全 RFC，而是**设计接口时能立刻判断该返回哪一个**。
> 全部结论都以 `AI ChatKit` 本机实测或源码为准。

---

## 一、先记住心智模型（比背码表重要）

> **状态码不是"我的程序出了什么事"，而是"我对这次请求的回应是什么"。**

| 类别 | 含义 | 谁的错 | 我的代码状态 |
|---|---|---|---|
| **2xx** | 我做成了 | — | 正常 |
| **4xx** | **你的请求有问题，我主动拒绝** | **客户端** | **正常运行**（它成功地判断出"不该接受"） |
| **5xx** | 我承诺能做到，但我没做到 | **服务端** | **出错了** |

### 最常见的错误：把用户的错误当 500 返回

用 500 回答"你传错格式了"，等于告诉运维**"服务器有 bug"**——把一个用户错误变成一次线上告警。半夜被叫起来查一个不存在的故障，就是这么来的。

**判断口诀：如果我的代码运行正常、只是拒绝了这个请求 → 4xx。如果我的代码真的挂了 → 5xx。**

## 二、你一定会用到的状态码

### 2xx 成功

| 码 | 名字 | 什么时候用 |
|---|---|---|
| **200** | OK | 一般成功。也是**流式接口唯一能用的成功码**（见第五节） |
| **201** | Created | **创建成功**。项目里 `POST /employee/add` 用的就是它 |
| **202** | Accepted | **已受理，但还没做完**（异步任务）← ResearchPilot 处理论文时必须用 |
| **204** | No Content | 成功但**没有响应体**。项目里 `DELETE /employee/delete/{id}` 用的就是它 |

**202 对你的意义**：上传一篇论文后要解析 PDF、切块、算 embedding，可能要几十秒。**不可能让一个 HTTP 请求干等这么久。** 正确做法是立刻返回 `202` + 一个 `task_id`，让前端另外去查任务状态。

→ 这就是改造 #5 里"Agent Task API"存在的理由。

### 4xx 我拒绝（注意：代码没崩）

| 码 | 名字 | 什么时候用 |
|---|---|---|
| **400** | Bad Request | 请求本身有问题：格式坏了、参数互相矛盾 |
| **401** | Unauthorized | **你还没登录**（我不知道你是谁） |
| **403** | Forbidden | **你登录了，但没权限**（我知道你是谁，但你不能） |
| **404** | Not Found | 资源不存在 |
| **409** | Conflict | **冲突**：重复创建、当前状态不允许这个操作（如删除正在处理的任务） |
| **413** | Payload Too Large | **文件 / 请求体太大** ← 上传接口必写 |
| **415** | Unsupported Media Type | **格式不支持** ← 上传接口必写（传了 docx 而只收 pdf） |
| **422** | Unprocessable Entity | **看懂了，但内容不合法**。缺字段、类型不对。**FastAPI 用 Pydantic 自动返回** |

> **401 vs 403 记法：401 = "你是谁？"　403 = "我知道你是谁，但你不能。"**

### 422 有两种，含义完全不同（实测）

FastAPI 用同一个 422 表达"请求体不符合我声明的模型"，但底下是两类问题：

| 类型 | 含义 | 层次 | 实测响应体 |
|---|---|---|---|
| `json_invalid` | **JSON 本身读不了**（语法错） | 传输层 | `{"detail":[{"type":"json_invalid","loc":["body",4],"msg":"JSON decode error","ctx":{"error":"Expecting property name enclosed in double quotes"}}]}` |
| `missing` | **JSON 读懂了，但缺必需字段** | 业务契约 | `{"detail":[{"type":"missing","loc":["body","message"],"msg":"Field required"}]}` |

**分清这两者的意义**：一个说明请求**根本没成型**（客户端拼错了），一个说明请求成型了但**不符合契约**（客户端漏了东西）。排查方向完全不同。

> **顺带一个经验**：好的错误信息会告诉你"我查到哪个位置了、我期待什么"。上面那句 `Expecting property name enclosed in double quotes` 就是在说"位置 4 这里我期待一个键名"。**你以后自己写接口时，返回的错误也应该有这个质量。**

### 5xx 我崩了（这才是故障）

| 码 | 名字 | 什么时候用 |
|---|---|---|
| **500** | Internal Server Error | 未预期的异常（兜底） |
| **502** | Bad Gateway | **上游服务返回了坏响应** |
| **503** | Service Unavailable | 服务暂时不可用（过载 / 维护） |
| **504** | Gateway Timeout | 上游超时 |

> **502 你亲身经历过。** 你机器上的系统代理让 httpx 访问 Ollama 时返回 502——那时挂的**不是 Ollama，也不是你的代码**，而是**中间那一跳**。这就是 502 和 500 的区别：500 是"我坏了"，502 是"我依赖的东西坏了"。

## 三、哪些是框架自动给的，哪些必须你自己写

### FastAPI 自动给的

| 情况 | 码 | 说明 |
|---|---|---|
| 函数正常返回 | 200 或你声明的 `status_code=` | |
| Pydantic 校验失败 | **422** | **实测**：缺 `message` 字段时返回 `{"detail":[{"loc":["body","message"],"msg":"Field required"}]}` |
| 未捕获异常 | **500** | 兜底 |

### 必须你自己写的

| 情况 | 码 | 为什么框架给不了 |
|---|---|---|
| 文件太大 | **413** | 框架不知道"你的业务里多大算太大" |
| 格式不支持 | **415** | 框架不知道"你只收哪几种格式" |
| 重复 / 状态冲突 | **409** | 这是业务规则 |
| 异步受理 | **202** | 这是业务流程设计 |

**关键区别：框架能校验"技术合法性"（字段类型对不对），校验不了"业务合法性"（这篇论文是不是重复了）。** 后者必须你写。

## 四、落到 ResearchPilot 的接口上（改造 #5 预演）

| 接口 | 情况 | 该返回 |
|---|---|---|
| `POST /documents` | 上传成功，已开始后台处理 | **202** + `{task_id}` |
| | 不是 PDF / DOCX / MD | **415** |
| | 超过大小上限 | **413** |
| | 同一篇论文重复上传 | **409** |
| `GET /documents/{id}` | 文档不存在 | **404** |
| `GET /tasks/{id}` | 处理完成 | **200** + 结果 |
| | 还在跑 | **200** + `{status:"running"}` |
| | 处理失败 | **200** + `{status:"failed", reason:...}` |
| `GET /health` | 一切正常 | **200** + 各依赖状态 |
| | 数据库连不上 | **503**（不是 200，也不是 500） |

**注意上面两个"200"**——任务"还在跑"和"处理失败"为什么是 200，不是 404 也不是 500？

> 因为**任务这个资源存在，接口也正确地查到了它**。任务的状态是**数据**，不是**这次请求的结果**。用 404 会让调用方以为"任务不存在"，用 5xx 会让调用方以为"接口坏了"。

**这是一个很容易搞错的判断点：区分"请求失败了"和"请求成功，但结果是坏的"。**

## 五、流式接口的特殊约束（第 4 课实验四的延伸）

**一旦 SSE 的响应头已经发出去了，你就再也不能改状态码了。**

所以 `/chat/stream` 在业务失败时**仍然返回 200**。这不是 bug，是 SSE 的固有约束。失败只能作为**流里的一个事件**传出去：

```
data: {"type": "error", "content": "..."}
```

你项目里实测到了两类失败，表现还不一样：

| 失败类型 | 现象 | 有 error 事件吗 |
|---|---|---|
| 生成器自身抛异常 | 能 yield 一个 error 事件 | ✅ 有（但状态码仍是 200） |
| **业务层失败**（Tool 报错，如 Ollama 停了、代理 502） | 异常被 Tool 层吞成一段 **ToolMessage 文本** | ❌ **没有 error 事件** |

第二类就是你做实验四看到的：模型只是道了个歉，HTTP 200、error 事件 0 个。

**设计含义**：流式接口的"健康"不能靠状态码判断。要做监控，你得在**事件层**埋点，而不是在 HTTP 层。这是改造 #7 要解决的事。

---

## 六、一句话总结

> **2xx 我做成了；4xx 我拒绝（但我没坏）；5xx 我坏了。**
> **框架管"技术合法性"，你管"业务合法性"。**
> **流式接口一旦开口，状态码就锁死了。**
