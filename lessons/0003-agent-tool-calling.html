Agent 为什么会自己决定调用工具？

这一课要拆掉一个最容易误解的印象：不是程序去查数据库，是模型"申请"去查。 分清这两者，你后面才可能自己给 ResearchPilot 加工具。

本课的单一收获：能说清「模型决定 → Graph 编排 → Tool 执行 → 模型收结果」这条回路，并知道决策权到底在谁手里。
动手前先确认一件事。在新开的 PowerShell 窗口里运行 scripts\start-ai-chatkit.ps1，必须看到这一行： 
Loopback check: httpx reaches Ollama directly. OK
如果看到的是黄色警告，说明检索链是坏的，做实验三会得到错误的结论。先解决它，再回来。

为什么这一课重要

你最终要把 OA Assistant 换成 ResearchPilot，而 ResearchPilot 的核心是一批新工具：检索论文、抓取全文、查引用关系……

这些工具全都遵循今天要拆的这个回路。更关键的是：面试里最高频的那道题——"你怎么保证 Agent 不乱调工具、不乱编答案？"——答案就藏在这一课里。

四个实验

打开 http://localhost:3000。每个问题都开一个新对话，避免上下文干扰。

实验一：决策权在谁手里？

1
问：你能做什么？
观察：回答前有没有出现工具调用折叠面板？
2
新对话，问：jack 在哪个部门？
观察：这次有没有出现工具面板？点开它，看工具名和 input。
3
记住这两次的差别，然后往下看。
你会看到：两句话从同一个输入框、走同一个接口、发给同一个 Agent。唯一的差别是文字内容。 所以"要不要用工具"这个决定，不可能来自前端，也不可能来自那个固定的脚本——它只能来自模型读完你的话之后的判断。

这一节课最重要的结论就在这里：Tool 是一个被申请调用的能力，不是一个被自动执行的步骤。模型像研究员，它只能"申请使用仪器"，不能自己动手。

实验二：工具的参数是谁写出来的？

1
回到刚才 jack 在哪个部门？ 那条消息，展开工具面板，看 input 那一行。
2
你现在应该看到类似这样的内容：
Tool 1: get_user_department
input：{"user_name": "jack"}
3
新对话，换成 请问 human resource 这个部门都有谁？ 再观察一次工具名和 input 的变化。
你会看到：那个 JSON 里的字段名 user_name 是开发者预先定义的（写在工具函数上），但里面的值 "jack" 是模型从你的自然语言里抽出来的。

这就是 Tool Calling 的本质：你提供"说明书的格式"，模型负责填内容。 也解释了为什么工具的名字和参数描述写得越清楚，模型用得越准——它只看得见这些。

实验三（核心）：当手册里没有答案时，会发生什么？

1
新对话，问一个员工手册里没有的问题：
公司为员工提供宠物保险吗？请务必查阅员工手册并给出手册中的依据。
2
等它答完，展开工具面板，仔细看 tool 的 result——工具到底交给了模型什么材料？
3
最关键的一步：把模型的结论和它引用的证据并排放好，然后问自己一个问题——那些证据，真的支持那个结论吗？
你会看到（实测）：工具确实被调用，而且检索结果大部分是相关的——手册里关于保险、福利、工伤的段落被找出来了。模型通常还会自作主张换几个说法再查一遍（这叫"查询改写"，是它自己想到的）。
但注意两个细节：
① 10 段材料里有 2 到 3 段其实是无关的，比如 may take any action deemed appropriate to recover or protect its property.
② 模型的措辞可能有两种，而它们差别很大：
  · 「手册中并未提及宠物保险」——证据支持的表述 ✅
  · 「公司不提供宠物保险」——证据不支持的表述 ⚠️
本课的核心结论：这两句话不是一回事。

「手册没写」≠「事实上不存在」。公司完全可能通过手册之外的方式提供这项福利——补充保险、地方政策、单独协议。

而系统里没有任何一层能发现这个落差：检索层只管交材料，模型只管读材料，没人负责检查"结论有没有超出证据"。你多跑几次可能会看到不同的措辞——这正说明它是概率性的软约束，不是保证。

所以真正的失败模式不是"凭空编造"（模型通常不会），而是"从证据不足跳到结论成立"——也就是无根据的否定。这比防编造难得多，也有价值得多。

这正是 ResearchPilot 改造 #3（判断证据充分性 → 补充检索）要解决的问题。 也是面试高频题："你的 RAG 检索不到内容时你的系统怎么办？"

实验四：当工具坏掉时，系统会告诉你吗？

1
停掉 Ollama（在终端里结束它，或在它的界面里退出）。确认它真的停了。
2
新对话，问：请查阅员工手册，告诉我年假规定。
3
观察两件事：① 界面上有没有出现任何"错误"提示？② 模型的回答是什么口吻？
你会看到（我们实测过）：工具返回的是一条错误文本——Error: ConnectionError('Failed to connect to Ollama...')，模型重试一次、又失败，然后用很客气的语气告诉你"手册查询暂时故障"。

而界面上没有任何错误：HTTP 状态 200、SSE 正常结束、错误事件数量为 0。
4
关键对照实验：Ollama 保持关闭，新对话问：请用 get_user_department 工具查询 jack 所在的部门。
你会看到：这一次它成功了。 模型照样申请调用工具，工具照样返回了 {"name": "human resource", ...}。

同一个后端、同一个模型、同一个 Graph、Ollama 同样不可用——一个工具失败，另一个成功。唯一的差别是模型选了哪个工具。

为什么？因为 get_user_department 内部只查 SQLite；而 search_handbook 内部必须先用 bge-m3 把 query 变成向量，而 bge-m3 跑在 Ollama 上。
所以：Ollama 只是某一个工具的实现细节，不是这个 Agent 的必需品。 这一点直接决定你将来能不能把 embedding 换成云端 API 或本地 ONNX 模型——而模型、Graph、Prompt 一行都不用改。

5
做完记得重新启动 Ollama，否则实验一到三都会失败。

这一课的第二条重要结论：错误被转换成了语言。Tool 层的异常变成了 ToolMessage 里的文本，模型读到文本后决定"礼貌地失败"而不是崩溃。用户看到的不是一个故障，而是一句道歉——从系统监控的角度看，这等于什么都没发生。

这就是"分层排查"为什么是硬功夫：同一句"查不到"，可能来自前端、HTTP、Graph、模型决策、Tool、Embedding、向量库中的任何一层，而现象看起来一模一样。

把观察翻译成系统职责

你的提问
   ↓
模型读懂意图  ←──── 决定权在这一层（它读你给它的工具"说明书"）
   ↓  输出"结构化意图"：我要调用 get_user_department，参数 user_name="jack"
Graph 接住这个意图，把请求路由到对应工具
   ↓
工具真正动手：查 SQLite 或查 Chroma
   ↓  把结果包成一条 ToolMessage
模型收到结果  ←──── 也可能收到空字符串、无关片段、或一段错误文本
   ↓
写最终回答（或再申请一次工具调用，形成循环）
注意上面这张图容易读错一个地方：Graph 画在中间，但它其实是最外层的框。

这里有两个不同的看问题的角度，别混：

角度一 · 时间顺序（事件按先后发生，用户视角）：
模型判断 → Graph 路由 → 工具执行 → 模型再判断 → 模型写答案
这个顺序是对的。

角度二 · 调用归属（谁启动谁）：
FastAPI → Graph → [ model 节点 → LLM ] + [ tools 节点 → Tool ]
这个角度下，Graph 在最外层——是它决定"现在该跑 model 节点了"，于是去调用 LLM。

为什么值得分清：如果 Graph 只是"中间一步"，它就管不了循环；正因为它是最外层的框，它才能决定"能循环几次""哪条边合法"。这才是它能约束一个 Agent 的原因。
角色负责不负责
模型（DeepSeek）决定用不用工具、填什么参数、怎么用结果写答案不直接碰数据库，也不能执行任何代码
Graph（LangGraph）规定"思考→用工具→再思考"的合法顺序，并接住模型的申请不判断该不该用工具
Tool真正执行查询，把结果包成消息不判断结果是否相关、是否足够
Embedding + 向量库把文字变成可比较的向量，再找"最近的 N 条"不设"够不够近"的门槛，也不说"没找到"

记忆句：模型提议，Graph 编排，工具执行，结果回读；没有人负责判断证据够不够。

30 秒自测

第 1 题：「jack 在哪个部门」这个答案，从提问到最终回答，先后经过了哪几层？（按顺序说出关键角色即可）

第 2 题：工具面板里 input：{"user_name": "jack"} 这段 JSON，是谁写出来的？

第 3 题（连到你的项目）：实验三里，证据只支持「手册中未提及宠物保险」，而模型的措辞可能是「公司不提供宠物保险」。如果你要给 ResearchPilot 加一个 search_papers 工具，你会怎么处理这个落差？

你可以这样向我汇报：「实验三里，工具返回的是……，模型的回答是……。我的判断是：缺的是……那一层的能力。如果加 search_papers，我会……」
不用答得完美。把观察发给我，我会只纠正关键概念，并带你把这一课变成改造 #3 的设计草稿。

简历视角：这一课对应的面试问题

面试官会问你今天能答的部分
模型是怎么知道可以调用你的工具的？开发者把工具的名称、参数和用途描述交给模型；模型只看得见这些说明，所以描述质量决定调用准确率
模型会不会乱调工具？你怎么控制？决策权在模型，但可用工具集合、参数格式和 Graph 的合法路径都由你定义——控制点是"给它什么说明书"和"允许它走哪些路"
RAG 检索不到内容时你的系统怎么办？（今天只到这里：现有系统没有处理，这正是你要在 ResearchPilot 里加的能力）
线上报错你怎么定位？先判断是哪一层：前端 / HTTP / Graph / 模型决策 / Tool / Embedding / 向量库。今天你已经见过一个"HTTP 200 但答案是错的"案例
