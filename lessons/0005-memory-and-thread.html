多轮对话是靠什么记住的？

你可能会以为"AI 记得我刚才说的话"。它不记得。它每次都被重新告知了一遍。 这一课要把这个幻觉拆掉——因为拆掉之后，你才知道改造 #6 要改的到底是什么。

本课的单一收获：能说清「记忆」是后端按 thread_id 保存并回放消息历史的结果，并且知道这份记忆存在哪里、什么时候会丢、以及它的代价是什么。
前置检查。这一课需要：后端 8001、前端 3000 在跑。不需要 Ollama（我们只聊常识，不触发检索）。 但实验三里你要重启后端，所以建议用手动方式启动后端，这样你能看到日志： 
cd D:\Code\agent\ai-chatkit-master\backend
$env:NO_PROXY = '127.0.0.1,localhost,::1'
.\.venv-py311\Scripts\python.exe -m uvicorn main:app --app-dir app --host 127.0.0.1 --port 8001

先做一个决定性实验

实验一：同一个会话 vs 换一个会话

打开 http://localhost:8001/docs，用 POST /chat/invoke（它返回一整块 JSON，好读）。

1
第一次请求，记住这个 thread_id：mytest-a 
{
  "thread_id": "mytest-a",
  "message": "记住一个数字：47。请只回复「已记住」两个字。"
}
2
第二次请求，thread_id 还是 mytest-a： 
{
  "thread_id": "mytest-a",
  "message": "我刚才让你记住的数字是多少？只回复数字。"
}
3
第三次请求，把 thread_id 换成 mytest-b，问同样的问题。
你会看到（实测）：
轮次thread_id回答
1（让它记住）mytest-a"已记住"
2（问它）mytest-a"47" ✅
3（换会话再问）mytest-b"我无法保留之前交流的内容…" ❌
同一个模型、同一个后端、同一个问题——只有 thread_id 不同，结果就完全不一样。

所以"记住"到底是什么？

看第三轮那句话："我无法保留之前交流的内容"——**模型说的是实话。** 它本来就没有记忆。

真相是：后端每次都把这段会话的历史消息，连同你的新问题，一起发给模型。

第 1 轮发给模型的内容：
   [系统提示词] + [用户：记住一个数字47…]

第 2 轮发给模型的内容：
   [系统提示词] + [用户：记住一个数字47…] + [AI：已记住] + [用户：是多少？]
                                                    ↑
                                        这一整段是后端"回放"给它的

第 3 轮（thread_id = mytest-b）发给模型的内容：
   [系统提示词] + [用户：是多少？]
                    ↑
        干净的一张白纸——所以它当然不知道
核心认识：模型没有记忆。"记住"是后端替它记住，然后每次重新讲给它听。

这解释了一个你以后一定会遇到的问题：对话越长，每次发给模型的内容就越多——输入 token 持续增长，所以长对话会越来越慢、越来越贵。
这也解释了为什么"新对话"能省钱：它换了一张白纸。

那后端把历史存在哪里？

角色在这个项目里特点
钥匙thread_id同一个 id = 同一份记忆；换 id = 换一份记忆
仓库后端的一个内存对象（checkpointer）存在进程内存里，后端一重启就全没了
前台展示浏览器的 localStorage存在你的浏览器里，关页面、重启电脑都还在

注意最后两行是两个完全不同的地方。 这就是下一实验的关键。

实验二（核心）：让后端"失忆"，看会发生什么

1
打开 http://localhost:3000，随便聊几轮，说点具体的事（比如"我最喜欢的颜色是蓝色，请记住"），确认它回答正确。
2
记下这个会话的 URL（形如 /chat/xxxx-xxxx），刷新页面，确认历史消息还在。
3
现在重启后端。在跑后端的那个终端按 Ctrl + C，然后重新启动它（用上面那条命令），等它就绪。
4
回到浏览器那个旧会话（前端不用刷新也行），问：我最喜欢的颜色是什么？
你会看到：界面上还显示着你刚才说的"蓝色"——但模型会告诉你它不知道。

因为：前端的历史在浏览器里，没丢；后端的记忆在进程里，重启就没了。 两边看起来一致，实际是两份互不相干的数据。
这不是一个 bug，是一个架构选择暴露出来的边界。 用户看到的现象是"AI 突然失忆了"——但真实原因是"存储介质不同"。

这类问题的专业说法叫"状态不一致"：同一份逻辑状态被存在两个地方，各自演化，迟早对不上。

这正是改造 #6（数据层）要解决的核心问题：把记忆从进程内存搬到真正的数据库（PostgreSQL），它才能重启不丢、才能支持多个后端实例、才能被查询和分析。

实验三：在界面上确认"新对话 = 换记忆"

1
在同一个对话里说：我的工号是 8888，请记住。
2
问：我的工号是多少？ —— 应该答对。
3
点左侧的 NEW CHAT，然后问同样的问题。
你会看到：新对话里它不知道工号。

因为"NEW CHAT"这个按钮做的事，本质上就是"换一个 thread_id"。 左侧那个会话列表里，每一项对应一个 thread_id；点进去就是把那个 id 重新设为当前会话——于是后端又把对应的那份历史回放给模型。

你现在可以完整理解那个界面了：会话列表 = 记忆的索引。点一下 = 取出那份记忆。 而"删除会话"删掉的是浏览器里的记录——后端的记忆并不会因此释放（它还在内存里，直到进程重启）。

把它接回你已经学过的链路

前端带着 thread_id 发请求
      ↓
后端用 thread_id 去 checkpointer 取出这一整段会话的历史
      ↓
把 [系统提示词] + [历史消息] + [你的新消息] 一起交给 Graph
      ↓
Graph 的 model 节点把这一整包交给 LLM        ← 模型第一次看到"历史"
      ↓
模型写回答（这一轮它"知道"上文了）
      ↓
回答被追加进 checkpointer 里那份历史
      ↓
下一轮重复上述过程

记忆 = 钥匙（thread_id）+ 仓库（checkpointer）+ 每轮回放。

改造 #6：SQLite → PostgreSQL记忆必须从内存搬到数据库。否则：重启丢、不能多实例、不能查询"用户在哪些会话里问过什么"

改造 #8：Evaluation评估要能复现。如果记忆在内存里、一重启就没了，你的评估结果就不可复现
