一次请求在网络上长什么样？

前三课讲的是"系统内部谁负责什么"。这一课往下钻一层：浏览器和后端之间，真正被传来传去的到底是什么东西。 做完这一课，你就能自己设计 ResearchPilot 的新接口了。

本课的单一收获：能看懂一次 HTTP 请求与响应，并说清 SSE 到底是什么——它不是新协议，它只是一个不结束的 HTTP 响应。
前置检查。这一课不需要 Ollama（我们只问常识问题，不触发检索）。只需要：后端在 8001、前端在 3000 上跑着。检查一下 http://localhost:8001/docs 能打开就行。

先破除一个印象

你之前可能觉得 localhost:8001/docs 是个"网页"，所以后端也能做前端。不是的——那个页面是 FastAPI 自动生成的开发者调试工具（基于 OpenAPI 规范）。它是后端顺手送的一张"说明书"，不是产品界面。

而它最有用的一点是：你可以绕过前端，直接和后端说话。 这一课我们全程用它。

实验一：认清后端的"门牌号"

1
打开 http://localhost:8001/docs。你看到的是这个后端公开的所有接口。
2
找到 chat 这一组，注意里面有两个很像的接口：POST /chat/invoke 和 POST /chat/stream。
3
数一下整个后端一共有多少个接口。（提示：除了 chat，还有 employee 和 department 两组。）
你会看到：后端一共公开了 15 个接口：2 个 chat、6 个 employee、7 个 department。

观察两件事：① 每个接口都由"方法 + 路径"唯一确定，比如 POST /chat/stream——方法不同或路径不同，就是不同的接口（GET /employee/get/1 和 DELETE /employee/delete/1 是两回事）。② 前端只用了其中 1 个（POST /chat/stream）。其余 14 个接口前端根本没碰——它们是为别的用途准备的。

实验二：手动发一次"非流式"请求

1
展开 POST /chat/invoke，点右上角 Try it out。
2
把 Request body 换成这段（把 message 改成你要问的常识问题）：
{
  "thread_id": "lesson4-invoke",
  "message": "用一句话解释什么是向量数据库",
  "agent_id": "oa-assistant"
}
3
点 Execute，然后往下看 Response body。等它整块出现。
你会看到（实测）：一个完整的 JSON，形如： 
{
  "type": "ai",
  "content": "向量数据库是一种专门用于存储、索引和检索高维向量数据的数据库…",
  "tool_calls": [],
  "tool_call_id": null,
  "run_id": "4bf6137b-7610-4ef1-9dc1-ba0462b696eb",
  "response_metadata": {
    "finish_reason": "stop",
    "model_name": "deepseek-flash"
  },
  "custom_data": {}
}
这个接口一次性返回。在它算完之前，你屏幕上什么都没有。

认识这几个字段：content 就是答案正文；run_id 是这次请求的唯一编号（用来排查问题、记录反馈）；tool_calls 如果非空，说明模型这次调用了工具；finish_reason: "stop" 表示模型正常说完，不是被截断。

实验三（核心）：同一个问题，换成"流式"

1
展开 POST /chat/stream，点 Try it out，填入同一段请求体（把 thread_id 换成 lesson4-stream）。
2
点 Execute，观察 Response body 是怎么出现的——和上一次有什么不同？
3
再回到 experiment 二的 /chat/invoke 发一次同样的问题，对比"答案出现的节奏"。
你会看到（实测）：响应是一行行冒出来的，长这样（逐字，注意每行结尾有两个换行）： 
data: {"type": "token", "content": "\u5411\u91cf"}
                                  ← 这里是一个空行
data: {"type": "token", "content": "\u6570\u636e\u5e93"}
                                  ← 空行
data: {"type": "token", "content": "\u662f\u4e00\u79cd"}
                                  ← 空行
……
data: {"type": "end"}
实测那次一共 121 行，其中 58 个 token 事件 + 1 个 message 事件 + 1 个 end 事件。把它们拼起来就是完整答案。
核心认识：SSE 到底是什么？

SSE = Server-Sent Events = 一个"不结束"的 HTTP 响应。

它没有新协议、没有握手、没有长连接魔法。就是：后端把 HTTP 响应的头先发出来，然后不关闭这个连接，持续往里面写文本。文本格式只有两条规则：
① 每一条消息以 data: 开头；
② 消息之间用空行分隔。

就这么简单。你看到的那个 content-type: text/event-stream，就是在告诉浏览器："这个响应不会一次性结束，你别等它结束，边收边处理。"

所以本质上是：普通 HTTP + 约定好的文本格式 + 不关连接。

为什么需要它？因为如果等答案全写完再返回（像 /chat/invoke），用户要盯着空白屏幕十几秒。流式让第一个字在几百毫秒内就出现——这不是花哨，这是体验的生死线。

仔细观察那一串 \u5411\u91cf：这是 JSON 在转义中文（向量）。意思是：中文在网上不是"字"，是一串编码。 前端 JSON.parse 之后才能看到"向量"两个字。这一点在实验五会变成一个大坑。

实验四：故意发一个错的请求，看后端怎么拦你

1
回到 POST /chat/stream，Try it out，把请求体里的 "message" 那一行整行删掉：
{
  "thread_id": "lesson4-bad",
  "agent_id": "oa-assistant"
}
2
Execute，看响应码和响应体。
你会看到（实测）： 
HTTP/1.1 422 Unprocessable Entity
server: uvicorn
content-type: application/json

{"detail":[{
  "type":"missing",
  "loc":["body","message"],
  "msg":"Field required",
  "input":{"thread_id":"lesson4-bad","agent_id":"oa-assistant"}
}]}
注意这个报错有多具体：它告诉你缺的是 body（不是 query、不是 path）里的 message 字段，类型是 missing，原因 Field required，还把收到的原始内容回给你看。

这不是人类写的报错，是 FastAPI 用 Pydantic 模型自动校验出来的——你只声明了"请求体长什么样"，校验、报错、文档全都自动生成。

422 是"能看懂但内容不对"（Unprocessable Entity）。对比几个常见的：

状态码含义在本项目里什么时候出现
200成功正常聊天
404找不到GET /employee/get/999（员工不存在）
422看懂了，但内容不合法缺 message 字段
500后端自己崩了代码里的 bug（比如之前发现的部门写接口）

实验五：一个真实的中文乱码坑

1
对比刚才两个接口的响应头里的 content-type。在 Swagger 里往下翻，找 Response headers。
你会看到（实测）：两个接口不一样！
接口content-type
/chat/invokeapplication/json ← 没有声明编码
/chat/streamtext/event-stream; charset=utf-8 ← 声明了
差别是会咬人的。 我在给你准备这一课时就踩到了：用 PowerShell 请求 /chat/invoke，拿回来的中文全是 åéæ°æ®åº 这种乱码；而请求 /chat/stream 就完全正常。

原因：application/json 没写 charset，某些客户端（比如 Windows PowerShell 5.1）就会去"猜"编码，猜错就乱码。严格说 JSON 默认就该是 UTF-8，是客户端不守规矩；但显式写上 charset 能省掉一整类诡异问题。

记住这条经验：只要你的系统要处理中文，编码就是一个会出现诡异故障的地方——而且故障长得不像编码问题，而像"数据错了"。ResearchPilot 要处理论文，中文/英文/希腊字母/公式符号全都有，这一条你会再遇到。

把两条路径并排看

【/chat/invoke 非流式】
前端 ──请求──→ 后端
                  │（用户盯着空白屏幕等…）
                  │  跑 Graph、调 LLM、等它说完
                  ↓
前端 ←── 一整块 JSON ──┘        用户：突然出现一整段答案

【/chat/stream 流式】
前端 ──请求──→ 后端
                  │  HTTP 头发出去，连接不关
                  │  data: {"type":"token","content":"向"}   ← 第一个字先到
前端 ←────────────┤  data: {"type":"token","content":"量"}
   （逐字渲染）   │  data: {"type":"token","content":"数"}
                  │  ...
                  └─ data: {"type":"end"}   ← 后端主动收尾

两个接口跑的是同一个 Graph、同一个模型。 唯一的区别是"结果怎么往外送"：一个等齐了再送，一个边算边送。

而前端那个 useStreamChat.ts 做的事，你现在可以完整理解了：它用 response.body.getReader() 逐块读取字节，然后按行切开、只处理 data: 开头的那几行、JSON.parse 之后看 type：是 token 就追加到当前消息后面（于是逐字显示），是 message 就更新工具面板，是 end 就停止转圈。
