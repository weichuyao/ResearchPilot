阶段 B · 动手 01 · 第一次修改业务代码

让三个坏接口工作起来

这是你第一次改这个项目的代码。所以先立两条规矩，再开工。

规矩一：先讲清为什么，再动手。
你要先把"这个接口为什么坏"讲给我听，我确认之后再改。理由很实际：改对了但你不知道为什么，那块能力就还是我的，不是你的。

规矩二：我评审，不代改。 代码由你写。你卡住了可以问，我不会直接给你答案——但我会给你足够的线索。
本课的单一收获：掌握一条真实工作流的完整节奏——观察现象 → 读日志定位 → 说清根因 → 改动 → 验证。
其中"读日志定位"是最值钱的一步，因为现实中没有缺陷清单给你看。

第 0 步：先给改动装一个"撤销键"

这个项目不是 git 仓库。也就是说：你现在改代码，改坏了没有任何回滚办法。

而且还有两个理由让你必须现在做这件事：

  • 简历项目最终必须上 git。 没有版本历史，面试时你没法展示"我改了哪些、为什么改"。
  • 后面还有 10 项改造要做。没有撤销键就动手，等于不系安全带上高速。
但不能直接 git init。 我先量过了，现在直接初始化会把 1.9 GB 的垃圾加进仓库：
目录大小该不该进仓库
.uv-cache660 MB❌ 依赖缓存
.pnpm-store334 MB❌ 依赖缓存
frontend/node_modules331 MB❌（已在 .gitignore）
frontend/.next311 MB❌（已在 .gitignore）
backend/.venv-py311304 MB❌ 没在 .gitignore 里！
__pycache__ × 341 个—❌ 编译产物
现有 .gitignore 只覆盖了 5 条，漏掉了 .venv-py311、.uv-cache、.pnpm-store、__pycache__。

所以顺序是：先补 .gitignore → 再 git init → 再第一个 commit。

第 1 步：手动启动后端（为了能看见日志）

1
如果后端正在跑，先停掉它。然后用这条命令手动启动——关键是日志会打在你眼前：
cd D:\Code\agent\ai-chatkit-master\backend
$env:NO_PROXY = '127.0.0.1,localhost,::1'
.\.venv-py311\Scripts\python.exe -m uvicorn main:app --app-dir app --host 127.0.0.1 --port 8001

为什么必须手动启动？因为你平时用的一键脚本是用隐藏窗口启动后端的——日志你看不见。而这一课的全部线索都在日志里。

（顺带说：这就是改造 #7「日志」要解决的短板。你刚体感到的那个痛点，就是那个改造项的动机。）

第 2 步：观察故障（什么都不要改）

打开 http://localhost:8001/docs，或者用 curl。把三个写接口都打一遍，记录状态码。

动手前先记下数据基线（改完要核对没被破坏）： 
department： 1 行 —— id=1, name='human resource'
employee：   1 行 —— jack, HR, department_id=1
调用请求体 / 参数实测结果
POST /department/add{"name":"试一下"}500
PUT /department/update/1{"name":"试一下"}500
DELETE /department/del/9999用不存在的 id 更安全500
GET /department/1（对照组）—200 ✅
注意一个关键细节：500 的响应体只有一行字—— 
HTTP/1.1 500 Internal Server Error
content-length: 21
content-type: text/plain; charset=utf-8

Internal Server Error
没有文件、没有行号、没有异常类型。 这是有意为之：把内部错误暴露给客户端是安全风险。

所以真正的线索只在两个地方：后端终端的日志，和你的代码。

顺便观察：读接口是好的（200），只有写接口坏。这个不对称本身就是线索——说明问题不在数据库连接、不在模型定义、不在路由注册，而在写操作那几行代码里。

第 3 步：读日志，定位根因

回到跑后端的那个终端，往上翻。你会看到 traceback——它会告诉你：异常类型 + 出错文件 + 出错行号。

提示：三个接口不一定是同一个原因。 仔细看那三段 traceback，它们可能给出不止一种异常类型。别看到一个就以为全找到了。
到这一步就停下，不要改代码。

把你找到的东西发我，格式：
  • 三个接口各自的异常类型（比如 XXXError）
  • 各自出错的文件和行号
  • 你的解释：这一行为什么会报这个错？
  • 你的修法：打算怎么改，为什么这么改
我确认之后再动手。这一步是这一课的核心——因为以后工作中没有 baseline-defects.md 给你看。

第 4 步：修改

我确认你的判断之后，你改代码。一个非常有用的小技巧：这个项目里有一个已经写对了的对照组——同样是"仓库类"，同样是增删改查，它的写法是正确的。找到它、对比它，你会发现这三处错的修法几乎是照抄。

（提示：去看另一个 repository 文件。它的 create / update / delete 三个方法是怎么写的？）

如果你已经看过 reference/baseline-defects.md：那份清单里确实写了这三处的行号。但建议你先自己从日志里走一遍——因为那份清单是我给你的，而"从日志定位"是你自己的能力。两者价值差很远。

第 5 步：验证（这才是"改完了"）

改完之后，重启后端（uvicorn 默认不带热重载，改了代码必须重启），然后重新打这三个接口：

调用期望的状态码为什么是这个码
POST /department/add201创建成功。路由里声明了 status_code=201
PUT /department/update/1200更新成功，并返回更新后的对象
DELETE /department/del/{id}204删除成功且无响应体
GET /department/200并且你新建的部门应该出现在列表里

改完也别忘了核对 employee 数据没被牵连（GET /employee/get_all）。

第 6 步（进阶）：你一定会撞到的第二个 500

修完上面三处之后，试着再添加一个名字已经存在的部门：

POST /department/add
{"name": "human resource"}     ← 这个名字已经存在

数据库的 department 表上有一个 唯一索引（uniq_department_name）。所以这一次，数据库会拒绝。

请回答三个问题：
  1. 这一次会发生什么？（还是 500 吗？）
  2. 这一次的 500 和前面那三个 500，性质一样吗？ 提示：前面三个是"我的代码写错了"，这一次是什么？
  3. 你觉得它应该返回什么状态码？为什么用 500 是错的？
这一问正好用上你刚学的状态码——4xx 是"我拒绝（但我没坏）"，5xx 才是"我坏了"。 想一想：用户重复提交，是我坏了吗？

这一问没有标准代码答案。你要做的是一个设计判断：在哪里拦（路由层还是仓库层）、拦到什么程度、返回什么。这属于改造 #5 的范围，提前想一想没坏处。

交给我什么

第一阶段（改之前）
  • 三个接口的异常类型 + 出错文件行号
  • 你的根因解释
  • 你打算怎么改
第二阶段（改之后）
  • 你改动的代码（贴出来）
  • 三个接口 + 读接口的验证结果（状态码）
  • 数据基线有没有被破坏
  • 进阶题的三问答案
